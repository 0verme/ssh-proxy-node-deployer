# SSH Proxy Node Deployer

Use this skill when the user asks to deploy, rebuild, or maintain a personal proxy node on a VPS they own or administer. It works across hosting providers by using SSH and inspecting the actual OS/network; it does not assume access to a provider console or API. The skill is self-contained: do not rely on another chat or user-specific history.

Use the defaults below whenever the user leaves a deployment choice unspecified. Ask the mode question at onboarding unless the user already chose; otherwise ask only for missing connection details or when a concrete safety conflict needs the user's decision.

## Q&A onboarding: choose a connection mode first

At the start of each deployment, ask this single-choice question in the user's language unless they already chose a mode: “新手模式：按初始 SSH 用户身份创建/复用 `vps` 或复用当前用户，并部署默认节点；高手模式：复用现有 SSH；如果只有 root 登录，可选择初始化管理员账号或暂停，并自定义高级选项。” Then follow the selected flow. In beginner mode, ask for the server address, the initial SSH username, and port (default `22`). In expert mode, ask for an existing SSH Host alias or configured target.

- **Beginner mode, initial SSH user `root`:** the user's explicit selection of Beginner mode for this deployment authorizes only the documented default `vps` bootstrap; a root login or deployment request alone does not. After direct-connect verification and read-only inspection, report the plan and create `vps` only if it does not exist; audit and safely reuse an existing `vps` without overwriting its password, keys, groups, or other settings. For a newly created `vps`, configure a dedicated Ed25519 key and password-required sudo. For an existing `vps`, reuse its working authentication and sudo as-is; stop if either is missing or conflicting. Independently verify a fresh `vps` SSH login and sudo before deployment. Keep the root system account and its SSH access unchanged by default.
- **Beginner mode, initial SSH user is not `root`:** reuse that exact account (including `ubuntu`, `debian`, `overme`, or `vps`). Never create `vps`, rename the account, or change its password, SSH keys, or SSH policy. Check whether the current account has the required sudo access; if not, report the missing permission and stop before system changes.
- **Expert mode:** reuse the existing SSH user and OpenSSH authentication configuration by default, including configured `IdentityFile`, the SSH Agent when available, and standard default keys. An SSH Agent is optional: its stopped/unavailable state must never block a successful SSH login through another configured method. Preserve any already configured, independently verifiable non-root administrator. If the initial SSH identity is `root` and the read-only audit finds no usable non-root SSH administrator, show the user a choice to (1) create a new administrator (recommended), (2) name and verify an existing administrator without changing it, or (3) pause deployment. For creation, ask for a username, validate it against local Linux account rules and reserved/existing accounts, show the exact plan, and require a separate explicit confirmation before any account, key, sudo, or local SSH-config write. A declined or missing confirmation means no writes and no deployment. Existing accounts are only reused when their SSH key login and password-required sudo are independently verified; do not repair an existing account without a separately confirmed plan. If the user chooses pause, stop without changes. Expert mode allows a custom username and account strategy; beginner mode uses `vps` only for its initial-root branch. Advanced SSH and node/network options remain expert-only; “none” keeps defaults.

The account branch is determined only by the **initial SSH login identity**, captured before any `sudo`, `su`, or other privilege change. Never infer it from the effective user after elevation. If the initial identity cannot be established, stop before account changes.

Ask for only the connection details required by the selected mode. In **expert mode only**, ask once whether the user wants to change defaults or enable optional feature IDs (for example, `ports-high`, a Fusion Monster check, a panel, extra protocols, or network tuning); accepting `无` / `none` keeps the defaults. Do not present or ask about advanced settings in beginner mode. Beginner mode always uses the default profile for a new installation. If the user selects beginner mode while also asking for an advanced add-on, explain that add-ons are expert-mode choices and ask whether they want to switch modes.

In **both modes**, ask which client app(s) the user uses before generating client files. Allow multiple selections and offer familiar examples such as Shadowrocket, Clash Verge/Mihomo, sing-box, and v2rayN, plus “other” for a named app. This is a normal setup question, not an advanced feature. Generate only formats supported by the selected apps. If the user is unsure, ask what device/operating system they use, check current compatibility when needed, recommend a suitable choice, and get confirmation before generating that format.

For any newly created administrator, use a cryptographically secure generator for a password of at least 24 characters. The password is for local account authentication and sudo; do not enable SSH password authentication. Set and deliver the generated password only through a secure, non-recording interactive terminal. Never move it into chat, command arguments, environment variables, scripts, shell history, logs, transcripts, or ordinary output files. If this environment cannot both set and deliver it safely, guide the user to set a password through a secure TTY; do not generate and disclose it through an unsafe channel. If no safe TTY path is available, stop initialization. Never put private keys in the repository or logs.

## Default profile

- Install sing-box from its current official signed package source for the detected system. Use the official configuration format and validate with the installed version.
- Configure one personal client with VLESS + REALITY + Vision over TCP and Hysteria2 over UDP. Offer IPv4 and IPv6 endpoints only for address families that actually work on the VPS.
- For a new installation, default to `443/tcp` for REALITY and `443/udp` for Hysteria2. Expert mode may explicitly select `ports-high` for `46690/tcp` and `46691/udp`; `none` keeps the new-installation default. TCP and UDP are separate transports. Check each listener and provider rule independently and keep server and client ports aligned. Port 443 is common for HTTPS/HTTP3 and may improve compatibility on some networks; it does not guarantee connectivity or prevent identification or blocking. High ports do not hide the VPS IP or replace security controls. SSH alone cannot verify cloud firewall rules; report the provider-side rules needed and use external tests where possible.
- Before any account or deployment write, distinguish a genuinely new installation from a repeated run, maintenance, an existing sing-box inbound, an unclear sing-box installation, or an explicitly requested migration. Inspect existing configuration and listeners read-only. If any existing inbound is found or ownership/state cannot be established, do not apply new-install defaults: preserve existing node ports, client files, firewall rules, certificates, and credentials. Report the state and pause before node changes if ownership is unclear. `ports-443` never authorizes migration. Port migration requires a separate explicit request and a separately reviewed and confirmed plan with recovery; it is not part of default installation.
- Before any account or deployment write, inspect both selected protocol ports independently for IPv4 and IPv6, binding addresses and wildcard/dual-stack overlap, listener service and owner, and identifiable container port mappings and forwarding rules. If either selected port conflicts or availability cannot be established, stop the entire dual-protocol deployment, report the evidence and options, and wait for an explicit choice. Never automatically replace a port, switch to high ports, stop, delete, or overwrite an existing service. In beginner mode, suggest switching to expert mode for `ports-high` if useful, but do not switch modes for the user. Cancellation or lack of explicit plan confirmation means no writes. Recheck both ports after a new choice and immediately before binding; if a conflict appears, stop and preserve existing services.
- For REALITY, use a user-supplied target when given. Otherwise try `gateway.icloud.com`, verify the target from the VPS, and use another reachable TLS target only if needed. Do not claim any target or protocol guarantees bypass on every network.
- For Hysteria2, use Salamander obfuscation with a new random secret. If the user provides a domain and confirms DNS control, automatically use the current official ACME workflow for a publicly trusted certificate; this is part of the default profile and does not require a separate preference question. Open TCP/80 temporarily only if required and unused, then close it after issuance. If ACME would disrupt an existing service or require an unprovided DNS/cloud credential, use a new self-signed certificate instead and explain that skipping certificate checks weakens server identity verification.
- Check TCP/80 for HTTP-01 and TCP/443 for TLS-ALPN-01, including listeners, reachability and existing services. REALITY on TCP/443 does not imply TLS-ALPN-01 can use it; Hysteria2 on UDP/443 does not make TCP/443 available. Never stop an existing service to obtain a certificate or bypass certificate verification to mask a port or certificate error. If a challenge cannot run safely, report the conflict and use the existing ACME workflow and fallback conditions above; if the safe outcome is unclear, pause instead of redesigning the workflow or installing a website.
- Generate new UUIDs, REALITY key pairs, short IDs, HY2 passwords, obfuscation secrets, and certificates for each server/client. Never reuse credentials from a different host.
- Ask which client app(s) the user uses and generate the corresponding supported configuration format(s), with separate IPv4/IPv6 endpoints where supported. Do not assume a default client. Save client files under the current task's designated private output directory (create it if needed), outside the repository and public web roots; apply restrictive permissions where supported. Link the files in the final report. Do not publish a subscription page or QR code by default.
- Keep the sing-box API service and Dashboard disabled by default; node traffic does not depend on them. Leave them disabled on resource-constrained hosts unless the user explicitly requests management access and available resources are suitable. The official Dashboard is served through the API in sing-box 1.14.0 and later; verify the installed version and consult the [official API documentation](https://sing-box.sagernet.org/configuration/service/api/) before enabling it. When enabled, require a strong, non-empty API secret, bind the API to loopback by default, and recommend access through an SSH tunnel. Never expose an unauthenticated API or dashboard publicly.
- Do not install a web panel, subscription server, WARP, additional protocols, BBR/fq tuning, swap, or other system optimizations by default.
- Do not run or download Fusion Monster by default. See the optional checks below.

## SSH and credential handling

- Connect only to the target host the user identifies. Reuse the configured SSH connection in expert mode. When the current authorized login path requires a password, accept it only through a secure interactive terminal after the reachability check. Never put passwords in chat, command arguments, URLs, environment variables, scripts, shell history, logs, or saved SSH configuration.
- A password set for local account authentication or sudo does not imply SSH password login. Keep the existing sshd authentication policy unchanged; do not enable password authentication as part of account initialization.
- Do not execute an unreviewed remote one-click installer or pipe remote content directly to a shell. Use official installation instructions; inspect any script and verify its source before execution.
- Do not echo credentials. Do not disable host-key checking globally. On first connection or a changed fingerprint, verify from a trusted source when possible and stop on an unexplained mismatch.
- Preserve the current SSH port, users, login methods, root access, and keys except for an account initialization explicitly selected and confirmed by the user. SSH hardening is optional and requires an explicit user request.

## Account initialization and authentication

- Record the username used for the first SSH login before running any command that changes identity. Use that original login identity for all beginner/expert account decisions, even if a later command runs as root through `sudo` or `su`.
- Run ordinary remote work as a non-root account. In beginner mode, use the root connection only for the read-only audit and the planned one-time `vps` bootstrap; after independent verification, continue through `vps`. In expert mode, reuse an existing non-root administrator when available. When root-only initialization is explicitly confirmed, use root only for the read-only audit and authorized bootstrap; after independent verification, continue through the selected account and use `sudo` only where needed.
- Before any account write, record the exact initial SSH login identity and read-only audit: OS/account policy; current login user; local users, UID, home and shell; existing non-root administrators and whether each has a usable independent SSH key login and sudo; sudo installation, groups and effective password policy; sshd authentication settings; the requested username's existence; existing public keys and relevant account/SSH configuration. Do not infer the initial user from `sudo`, `su`, or an effective UID.
- For expert-mode initial `root` with no independently verifiable non-root SSH administrator, show: “Detected SSH login user: root. No configured and verifiable non-root SSH administrator was found. Choose: (1) create a new administrator (recommended), (2) specify and verify an existing administrator, or (3) pause deployment.” Option 2 is read-only and must not alter that account. If the named account lacks a working independent SSH login or password-required sudo, explain the failed check and offer to choose another account or pause; any repair requires its own exact plan and explicit confirmation.
- For the create option, ask for a custom username. Validate it before invoking any account tool: require a Linux-compatible login name (for example, ASCII `[a-z_][a-z0-9_-]{0,31}`), reject empty input, leading `-`, shell syntax, whitespace, reserved/system account names, UID 0, and any existing account unless it is being handled by the existing-account audit. Check local policy and UID ranges as well as the format. Pass the validated username as a distinct process argument; never interpolate unvalidated input into a shell command. Invalid input causes no writes and may be re-entered.
- Show a complete account initialization plan before writing, including username, whether it is new or existing, generated password length and secure TTY handling (never the secret itself), dedicated Ed25519 SSH key, password-required sudo, intended local SSH alias and key path, and that existing root access and sshd password-authentication policy remain unchanged. Ask for an explicit yes/no confirmation after presenting the plan. Before the first write, confirm a safe interactive TTY path is available either to set/deliver the generated password or to let the user set it themselves; if no safe TTY can be used, stop before account, key, sudo, or SSH-config changes. No confirmation, “no”, or cancellation means no account, key, sudo, SSH-config, or deployment changes.
- If the username does not exist and the user confirms, create a normal user with the system's standard account tool, home directory, and valid login shell. Generate a unique cryptographically random password of at least 24 characters for local authentication and sudo. Set and deliver it only through a secure non-recording TTY. If this cannot be done safely, ask the user to set their own password through a secure TTY and verify it there; if no safe TTY is available, stop without substituting a chat, file, argument, environment-variable, script, history, or log disclosure.
- Generate a dedicated local Ed25519 key under `~/.ssh/ssh-proxy-node-deployer/` (or another user-approved restricted directory) only after confirming that its directory and key files do not exist; never overwrite an existing key. Keep the private key local with restrictive permissions (typically directory `0700`, private key `0600`), and never upload it to the VPS. On the VPS, create the new user's `.ssh` directory with correct ownership and restrictive permissions (typically `0700`); append only the public key idempotently to `authorized_keys`, preserve any existing lines, and set correct ownership and restrictive file permissions (typically `0600`). Add a unique SSH Host alias with `HostName`, `User`, `Port`, `IdentityFile`, and `IdentitiesOnly yes`. Check both alias and key-path conflicts first; never overwrite a file, alias, or existing Host stanza. If either path conflicts, report it and ask the user for another alias/key path or to pause before writing. Validate the existing local SSH config first and prepare a backup/recovery copy before appending; validate the completed config with OpenSSH (`ssh -G <new-alias>` without exposing the full output), and restore only the task's exact appended block if validation fails. Keep every prior Host entry and authentication method unchanged.
- Grant sudo only to a newly created account, using the system's standard administrative group or a reviewed sudoers rule. Confirm effective sudo requires a password; never add or preserve `NOPASSWD: ALL` for this account. If sudo is absent or the current policy cannot provide password-required access without unsafe broad edits, stop and report the blocker. Do not alter sudo policy for an existing account without a separately confirmed plan.
- If the requested username already exists, do not recreate it or change its password, SSH keys, groups, sudo policy, shell, or SSH settings. Audit its existing public-key path and configuration, confirm a fresh independent SSH key login as that exact username, inspect `sudo -l`, clear the sudo timestamp, and verify `sudo -v` through a secure interactive password prompt. Reuse it only if the required key authentication and password-required sudo both pass. Otherwise report the conflict and let the user choose another name or pause.
- Keep the original root SSH session open throughout. From a genuinely independent new SSH connection using the new alias/key (or audited existing key), first confirm the remote login identity equals the selected username before any elevation. Then inspect `sudo -l`, clear cached sudo authentication with `sudo -k`, and verify `sudo -v` through a secure interactive TTY. Confirm the account has the system privileges needed for deployment and that sudo requires its password. Do not treat `su`, an already elevated or reused root session, or a post-sudo identity as independent SSH verification. If SSH or sudo verification fails, stop deployment, preserve root access, report exactly which changes occurred, and do not automatically delete the account or close any working access path.
- In beginner mode with any initial non-root login, reuse that exact user and its current authentication. Read-only check its sudo capability. Do not create `vps`, alter its groups, add keys, change its password, or modify SSH settings. If authentication fails or sudo is insufficient, report the specific failed check and the permission needed; stop without attempting privilege escalation or creating another account.
- In expert mode, never create or modify an account until the user explicitly selects the account action, reviews its exact plan, and confirms it. Prefer an existing non-root account that passes independent SSH and sudo verification. After a newly initialized or explicitly selected existing admin passes both checks, use it for subsequent deployment.
- Make account initialization repeatable: inspect whether the account, key, public-key line, sudo membership/rule, and local SSH alias already exist before writing. Do not duplicate users, keys, aliases, group memberships, or sudo rules. Existing accounts retain their credentials and policy; reuse an already-correct state or report conflicts and let the user reselect or pause.
- Never disable root SSH login by default. Do so only after a separate explicit request, a verified alternate administrator login, and a tested recovery path plus rollback plan. Check `sshd` syntax before reload/restart, preserve the active SSH session, and verify a second connection before considering the change accepted. Never delete the root system account or blindly modify a firewall.

## Workflow

### 0. Complete SSH prechecks before deployment

Keep these checks separate and run them in order: (1) a raw TCP probe to the target SSH endpoint, (2) an SSH authentication probe, and (3) an optional SSH Agent status diagnostic. A passing result from one check never substitutes for another.

#### 0.1 Raw TCP direct-connect check

After the user selects a mode and provides its required connection details, test the specified SSH port directly from the device and network they intend to use to reach the VPS (port 22 by default). In beginner mode, do this before requesting the password or creating/installing a key. If they specifically want to know whether port 22 is reachable, test 22 even when the configured SSH port differs, and report both results separately.

- Use a short-timeout raw TCP probe, such as PowerShell `Test-NetConnection` on Windows or `nc` on Linux/macOS. This probe does not use SSH `ProxyCommand`/`ProxyJump` or an HTTP/SOCKS application proxy. In expert mode, resolve only the effective target `HostName` and `Port` from the supplied SSH Host configuration (for example, read those fields from `ssh -G <Host>`); do not use the configured jump host as the TCP target. Do not print or upload the full `ssh -G` output. Do not silently disable a system VPN or tunnel; if one is active, report that the path may still be routed through it.
- If given a hostname, resolve it using the local resolver and report which address/family was tested. Test IPv4 and IPv6 separately when both are expected to work. Do not send the server IP to third-party checking sites.
- If the agent runs somewhere other than the user's client device/network, do not present that result as the user's direct-connect result. Give the user a local command to run, or clearly label the test location.
- Report a successful TCP handshake as “reachable from this test location”; it does not prove SSH authentication will succeed or that the address is unfiltered everywhere. A refusal usually means the port is closed or actively rejected. A timeout or unreachable result is inconclusive and can come from packet loss, routing, the server/provider firewall, a local network, or filtering.
- Never declare an IP “banned” from one failed probe. Check whether the SSH service uses a different port and whether host/cloud firewall rules or source-IP allowlists explain the result. If direct SSH access is a requirement and the port is unreachable, stop before deployment and report the evidence. Suggest one comparison from an independent network when useful; reachability from another network but not this one points to a network-specific path/filtering issue, not necessarily a globally banned IP.
- Do not fall back to a proxy or replace the server IP automatically. Let the user choose whether to retry from another network, continue via a specified route, or ask the provider about changing the IP.

#### 0.2 SSH non-interactive authentication check

After the raw TCP check passes, verify SSH authentication separately. In expert mode, first run exactly `ssh -o BatchMode=yes -o ConnectTimeout=10 <Host> "whoami && hostname"`, replacing `<Host>` with the user's existing OpenSSH Host alias. Do not add `-i`, replace the config file, disable host-key checks, or otherwise override the alias's authentication settings. This lets OpenSSH use the configured `HostName`, `User`, `Port`, `IdentityFile` (including multiple identities), certificate, `ProxyJump`, SSH Agent if available, and standard default key locations. `ProxyJump` may be used for this SSH authentication probe; it does not change or satisfy the separate raw TCP direct-connect result.

- Exit code 0 means SSH authentication succeeded. Record the returned login user and host, then apply the existing beginner/expert account policy. Do not require an SSH Agent when this or another authorized existing login method succeeds.
- If the command fails, distinguish a connection timeout, host-key verification error or changed fingerprint, `Permission denied` authentication failure, and other SSH/configuration errors. Report the category and a short diagnostic with any sensitive values removed, then stop before deployment. Do not edit SSH configuration, try other identities by rewriting the command, add keys, accept a host key automatically, use `StrictHostKeyChecking=no`, or bypass any safety check. A host-key problem must be resolved through the existing trusted fingerprint-verification process. The only permitted next authentication attempt is when the user has identified their existing authorized path as password-based; then use the secure interactive terminal described above after the raw TCP check. This is never an automatic fallback. Never put a password in command arguments, chat, scripts, environment variables, logs, or saved SSH configuration.
- Never print, copy, or upload private-key contents or passwords. Do not dump verbose SSH diagnostics or the full resolved SSH configuration. Report only what is needed to identify the failure safely.

#### 0.3 SSH Agent status (diagnostic only)

The SSH Agent is a separate, optional authentication helper. Its state may be reported as running, stopped, unavailable, or unknown when relevant, but it is not an authentication result or a deployment prerequisite. Do not start, enable, or reconfigure it automatically. A stopped Agent does not block authentication through a configured `IdentityFile`, a standard default key, or another successful OpenSSH method. If authentication fails, Agent state may be noted as context but must not replace the SSH error classification or be asserted as the cause without evidence.

### 1. Identify the host and inspect it before changes

If the SSH target or login method is missing, ask only for that detail. Validate the hostname/IP; do not connect over the public Internet to documentation, private, loopback, link-local, or reserved addresses unless the user confirms a private route/VPN. Then run read-only checks for:

- Distribution/release, architecture, package manager, systemd, available CPU/memory/disk, current sing-box installation and configuration.
- Public IPv4/IPv6 addresses, default routes, and whether each family is usable for inbound traffic. An assigned IPv6 address alone does not prove IPv6 reachability.
- TCP/UDP listeners and conflicts with the requested ports.
- Host firewall and existing rules. Keep these separate from cloud-provider firewall/security-group rules, which may not be visible over SSH.
- Services or configurations that a deployment might overwrite.

Do not perform a broad OS upgrade. If the OS/architecture is unsupported by current official sing-box installation guidance, or a safe install would overwrite an unrelated service, explain the specific issue and pause before changing it.

### 2. Account initialization and independent verification

After the read-only audit, report the deployment and account plan before any write. In beginner mode, initialize or audit/reuse `vps` only when the **initial** SSH user is root; otherwise reuse the initial user unchanged. In expert mode, reuse a verified non-root administrator when one exists; if initial SSH identity is root and no verified non-root administrator exists, ask whether to create a custom-name account, specify and verify an existing account, or pause. For creation, show and receive explicit confirmation of the complete plan before the first write. After any account action, complete the fresh independent SSH login, identity, `sudo -l`, cache-clear, and password-required `sudo -v` checks before installing or changing sing-box. Continue ordinary deployment as the verified non-root administrator and use sudo only for system changes. If the user requested assessment only, stop after reporting findings. If the user cancels, an account conflict occurs, secure TTY is unavailable, or SSH/sudo verification fails, stop deployment, explain the reason and any changes already made, and preserve root access.

### 3. Optional machine benchmark

Run Fusion Monster only when the user explicitly asks for a machine check, benchmark, or performance test. Use the maintained Go edition from the [official oneclickvirt/ecs repository](https://github.com/oneclickvirt/ecs), resolve one official release, download the matching OS/architecture asset, and verify it against that release's SHA-256 file before execution. Run it from a unique temporary directory; do not pipe an unreviewed script to a shell or install the benchmark globally.

When the user requests a basic check, use the current release's documented system-only profile: disable CPU, memory, disk, speed, route, media/IP-quality suites, logging, and public result upload; verify the upload-off flag and bound runtime to 25 seconds. Basic IP lookups may still send the VPS public IP to third-party information services; tell the user before running. If upload cannot be disabled, checksum verification fails, or a reliable time limit is unavailable, skip the benchmark. Clean only this run's temporary files on success, failure, timeout, or interruption, then continue deployment unless a finding makes the VPS unsafe or unsuitable.

Full benchmark mode is opt-in. It can create CPU/disk load and consume substantial bandwidth, so run it only when the user explicitly requests comprehensive tests. Never publish results unless the user explicitly asks.

### 4. Install with minimal, reversible changes

- Choose the official package instructions for the detected Linux distribution. Do not run unrelated repositories' one-line installers as root. If installing from a binary release, verify its official checksum/signature before use.
- If sing-box or its configuration already exists, inspect and back it up before changes. Add or update only the requested inbound; do not replace unrelated configuration or remove an existing service. If safe coexistence is not possible, pause and explain the conflict.
- Write secrets in protected files (directory `0700`, files `0600` where suitable). Keep Hysteria2 certificate/key private. Use the service account/permissions specified by the official package when possible.
- Validate configuration before restarting. Keep a rollback copy and do not reboot.

### 5. Preserve firewall and SSH access

- If a host firewall is active, add only the exact TCP/UDP node-port rules while preserving its existing policy. For HTTP-based ACME validation, open TCP/80 temporarily and remove that rule after issuance. Do not flush rules or replace the firewall implementation.
- If no host firewall is active, leave it that way by default; report the cloud firewall/security-group rules the user needs to add. Enabling a host firewall is an opt-in feature.
- If the user explicitly asks to enable a firewall or harden SSH, protect the current session, preserve the real SSH port, and use a timed rollback when supported. Verify a second SSH login before removing old access or canceling rollback. If access cannot be protected, stop before the risky change.
- Never claim to have changed a provider firewall unless an authorized provider integration was actually used.

### 6. Verify and deliver

- Check configuration validity, service health, listening sockets, firewall rules, and logs without exposing secrets.
- Test REALITY and HY2 over every available address family. Prefer a real client from outside the VPS. Label server-side self-tests separately from external tests; do not claim a handshake or usable tunnel without evidence.
- Generate configurations for the client app(s) selected during onboarding, with separate IPv4/IPv6 endpoints where supported. Generate QR codes or a private HTTPS subscription only when requested.
- Keep client files private and out of repositories, public pages, and commits. Do not print full credentials in progress updates.

## Optional features

The README lists stable feature IDs. The user can write `可选项：feature-id, feature-id` or `Optional features: feature-id, feature-id`; ordinary language requests count too. Enable only the named options. An omitted list, an empty list, or `无` / `none` means keep the default profile with no optional features. If an ID is unknown or its requested scope is unclear, ask instead of guessing. Feature IDs do not bypass the safety checks below or elsewhere in this skill.

Supported IDs:

- `ports-high`: explicitly select TCP/46690 for REALITY and UDP/46691 for Hysteria2 for a new installation; check both and stop on conflict without automatic replacement.
- `ports-443`: compatibility alias for the new-installation default TCP/443 and UDP/443; it never authorizes changing existing nodes. If `ports-high` and `ports-443` are both selected, stop and ask the user to choose explicitly before any writes.
- `domain-endpoint`: expert-mode explicit selection of a user-controlled client connection domain; follow the domain and REALITY contract below.
- `reality-nearby-target`: expert-mode explicit selection of passive candidate discovery and user selection.
- `reality-custom-target`: expert-mode explicit selection of a user-supplied handshake target.
- `fusion-basic`: run the documented, time-limited basic Fusion Monster check with upload and heavy suites disabled. Tell the user first that basic IP lookups may send the VPS public IP to third-party services.
- `fusion-full`: run a full benchmark only after explaining that it can load CPU/disk and consume substantial bandwidth. Never publish results unless separately asked.
- `firewall-ufw` / `firewall-firewalld`: set up the named host firewall only after checking current rules and preserving SSH access; do not replace an existing firewall blindly.
- `ssh-hardening`: harden SSH only after testing an alternate administrator login and preparing rollback. Confirm the intended changes if the user has not specified them.
- `protocol-anytls`, `protocol-tuic`, `protocol-shadowsocks`: add the named protocol. `protocol-other` requires the user to name the protocol.
- `multi-user`: add multiple users and separate credentials. `traffic-accounting`: add traffic/quota tracking; explain storage and accuracy limits before choosing a method.
- `warp`: configure WARP. `bbr-fq`: apply BBR/fq tuning. `swap`: configure swap. `udp-buffer-tuning`: change UDP buffer settings. Check compatibility and impact before applying system-wide changes.
- `sing-box-dashboard`: enable the official Dashboard only on sing-box 1.14.0 or later. Check resource headroom; keep it off on low-resource hosts unless the user explicitly accepts the trade-off. Require a strong, non-empty API secret and loopback binding with SSH-tunnel access by default. Direct remote exposure still requires a separate explicit request, TLS, and strict network restrictions.
- `third-party-panel`: install a third-party panel only when the user names the panel or approves a clearly described choice. Check resources, supported installation method, and exposure/security requirements first.

## Expert domain and REALITY target contract

These are logical Q&A parameters, not environment variables parsed by this repository. Collect only missing or invalid values after explicit expert-mode feature selection; never ask these advanced questions in beginner mode. `OPTIONAL_FEATURES=none` does not enable the new domain features. No owned domain is required for deployment. Merely providing a domain does not enable `domain-endpoint` or change a REALITY client endpoint. The existing beginner and expert Hysteria2 ACME trigger and fallback remain unchanged: independently ask what the domain is for and whether the user confirms DNS control; the existing default ACME rule still applies when its conditions are met.

- `domain-endpoint` asks for `ENDPOINT_DOMAIN`, a domain the user controls, and the specific client protocols and address families authorized to use it. The endpoint, REALITY SNI/handshake target, and Hysteria2 certificate domain are separate roles; do not infer one from another. Domain input alone is not permission to modify DNS or a REALITY target.
- `REALITY_TARGET_MODE` is `default`, `custom`, or `nearby`. No target feature means `default`, preserving the existing default target behavior. `reality-custom-target` selects `custom` and requires `REALITY_CUSTOM_TARGET`, a hostname and, if explicitly requested, its port (otherwise 443). `reality-nearby-target` selects `nearby` and asks for `REALITY_NEARBY_SCOPE`: `same-asn`, `same-prefix24` (IPv4 only), or `auto`. `auto` tries available passive same-ASN evidence then same-prefix24 evidence if available; report missing evidence and do not broaden into scans. Both target feature IDs together, a contradictory mode, invalid values, or `none` combined with feature IDs are conflicts: stop and ask for an explicit choice before any writes. Do not silently infer consent from a parameter alone.
- For the endpoint, inspect A, AAAA and CNAME chains with bounded resolution, detect loops, and record final addresses and relevant TTLs. Compare each final address against independently observed public VPS addresses; check actual IPv4/IPv6 availability and listener/client reachability separately. Identify ordinary CDN proxying using provider evidence and DNS behavior where possible; DNS-only cannot be proved solely by matching an address. Report uncertainty, mixed or stale records, NAT and split-horizon ambiguity.
